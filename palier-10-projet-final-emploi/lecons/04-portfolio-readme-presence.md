# Leçon 04 — Portfolio, README et présence en ligne : les 90 secondes du recruteur

> 🎯 **À la fin de cette leçon** : ton travail est présenté pour être compris en 90 secondes — un portfolio qui montre des projets finis, des README qui racontent, un GitHub et un profil professionnel soignés.
> ⏱️ 5 h · **Prérequis** : la leçon 01 (le pitch), un projet fini et déployé (leçons 02-03), et le Markdown/Git (palier 0).

---

## De quoi on parle

Tu as construit des choses solides. Mais un recruteur ne lira pas ton code : il **survole** ton profil en une minute et demie, et décide s'il creuse. Cette leçon rend ton travail **lisible en 90 secondes** par quelqu'un de pressé qui ne te connaît pas.

Trois surfaces :

- le **portfolio** : la page qui présente tes projets finis (le quoi, le pour qui, la démo, le code) ;
- les **README** : le premier fichier qu'on voit sur un dépôt GitHub — ce qui transforme un tas de code en projet compréhensible ;
- la **présence en ligne** : ton profil GitHub (épinglé, actif), ton profil professionnel (type LinkedIn), cohérents et à jour.

Le principe directeur : **tu écris pour quelqu'un qui ne te connaît pas et qui est pressé**. Pas pour toi, pas pour un expert qui prendrait le temps. Chaque projet doit se comprendre sans explication : quel problème, pour qui, démo en un clic, code lisible. Un projet génial mais incompréhensible en 90 secondes est, pour un recruteur, invisible.

---

## À quoi ça sert, concrètement

**Parce que le recruteur décide vite, sur peu.** Face à des dizaines de candidatures, il survole. Si en 90 secondes il ne comprend pas ce que tu as fait et que tu sais livrer, il passe. Ta présentation n'est pas de la cosmétique : c'est ce qui déclenche (ou non) l'entretien. Un bon profil ouvre les portes qu'un bon code, mal présenté, laisse fermées.

**Parce qu'un projet non présenté n'existe pas.** Du code sur GitHub sans README, sans démo, sans explication, est illisible pour un étranger — donc inexistant à ses yeux. Le README et la démo sont ce qui transforme ton travail en **preuve** visible. C'est le prolongement du « livrer » du palier 8 : non seulement en ligne, mais **montrable et compréhensible**.

**Parce que c'est la narration de ton parcours.** Ton projet multi-clients (leçon 02), ta fonctionnalité IA (leçon 03) racontent une histoire : « je sais concevoir, construire front/back/mobile, déployer, intégrer de l'IA ». Bien présentés, ils prouvent ta polyvalence. Mal présentés, ils se perdent. Le portfolio est là où ton parcours devient un argument.

**Et parce que la présentation est elle-même une compétence évaluée.** Un README clair, un profil soigné, montrent que tu communiques, que tu penses à ton lecteur, que tu as le souci du fini. Ces qualités comptent autant que le code — et un recruteur les lit comme un signal de professionnalisme.

## Où ça intervient dans le développement

La présentation est la couche visible de tout ton travail :

```
   TON TRAVAIL (projets finis, déployés — leçons 01-03, paliers 2-9)
        ▼  présenté pour un étranger pressé
   PORTFOLIO : la vitrine (projets, pitch, démos, liens)
        ├─ chaque projet a un README qui raconte (problème, démo, stack, code)
        ├─ GitHub épinglé et actif (les bons dépôts en avant)
        └─ profil pro (LinkedIn) cohérent, qui pointe vers tout ça
        ▼
   RECRUTEUR (90 secondes) → comprend → décide de creuser → entretien (leçon 05)
```

Trois ancrages.

**Le pitch vient de la leçon 01.** La phrase qui résume chaque projet (« ça aide [cible] à [bénéfice] en [comment] ») est le cadrage de la leçon 01. Un projet bien cadré se présente en une phrase ; c'est l'ouverture de chaque entrée de portfolio et de chaque README.

**Les projets à montrer sont ceux des leçons 02-03.** Le produit multi-clients (leçon 02) et la fonctionnalité IA (leçon 03) sont tes pièces maîtresses. Le portfolio les met en vitrine, avec la démo déployée (palier 8) qu'un clic suffit à ouvrir.

**Et le Markdown/Git vient du palier 0.** Le README est du Markdown (palier 0, leçon 05), le dépôt est sur GitHub (palier 0, leçon 04). Tu réutilises ces outils, cette fois au service de ta présentation professionnelle. C'est aussi le moment où les **templates** `readme-projet` du dépôt servent.

## Ce que tu verras quand tu travailleras

### Aujourd'hui, en solo

Tu vas écrire un README qui raconte ton projet (problème, démo, captures, stack, lancement), construire une page de portfolio qui présente tes projets finis avec leur pitch et leurs liens, épingler tes meilleurs dépôts sur GitHub, et soigner ton profil professionnel pour qu'il soit cohérent et pointe vers ton travail. Tout avec le test des « 90 secondes ».

### En équipe, en entreprise

**Le README est la porte d'entrée de tout projet.** En entreprise, le README d'un dépôt est ce qu'un nouvel arrivant lit en premier : à quoi sert ce projet, comment le lancer, où sont les choses. Un bon README fait gagner des heures à toute l'équipe. Savoir en écrire un est une compétence quotidienne, pas seulement pour le portfolio.

**La présence en ligne est regardée.** Recruteurs et futurs collègues regardent ton GitHub (activité, qualité des README, projets épinglés) et ton profil pro. Un GitHub soigné et actif est un atout concret ; un GitHub vide ou brouillon dessert.

**La démo vaut mille mots.** Un lien vers une app déployée, qu'on peut essayer en un clic, est infiniment plus convaincant qu'une description. C'est pour ça que déployer (palier 8) compte autant : ça transforme « j'ai fait une app » en « essaie-la ».

**La cohérence du profil compte.** Portfolio, GitHub, LinkedIn/CV doivent raconter la même histoire et pointer les uns vers les autres. Un recruteur qui trouve des informations contradictoires ou un profil à moitié rempli doute. La cohérence est un signal de sérieux.

### Ce qui sert tous les jours, et ce qui est rare

Tous les jours (en entreprise) : écrire et maintenir des README de projet, documenter comment lancer un projet.

Régulièrement (en recherche) : mettre à jour le portfolio, épingler les bons dépôts, soigner le profil pro, ajouter une démo et des captures.

Rare ou spécifique : un portfolio très designé, un blog technique, des contributions open source visibles, une présence sur les réseaux techniques. De bons compléments, mais le cœur reste : projets finis + README clairs + démos + profil cohérent.

## La mécanique

### Le test des 90 secondes

```
Montre ton portfolio/README à quelqu'un qui ne connaît pas ton projet, 90 secondes, puis :
  - A-t-il compris à quoi sert le projet ? (le problème, pour qui)
  - A-t-il vu qu'il est FINI et en ligne ? (la démo)
  - Saurait-il par où regarder le code ? (la stack, la structure)
Si non à l'une de ces questions → ta présentation échoue, pas ton projet.
```

C'est le critère de toute la leçon. On ne présente pas pour soi, mais pour un étranger pressé. Teste littéralement : fais regarder à quelqu'un, chronomètre, pose les questions. Ce qu'il n'a pas compris en 90 secondes est à clarifier.

### ⭐ Le README qui raconte

```
Un bon README de projet, dans l'ordre (le lecteur pressé lit de haut en bas) :
  1. TITRE + une phrase (le pitch, leçon 01) : "X aide [cible] à [bénéfice]."
  2. DÉMO : un lien vers l'app en ligne + une capture d'écran (ou un GIF). ← le plus important
  3. LE PROBLÈME : quel besoin réel ça résout (2-3 lignes).
  4. LES FONCTIONNALITÉS : ce que ça fait (les must-have, leçon 01).
  5. LA STACK : les technos, brièvement (React, Node, PostgreSQL, Flutter, Docker...).
  6. LANCER EN LOCAL : les quelques commandes pour l'essayer (si pertinent).
  7. (optionnel) ce que tu as appris, les choix d'architecture.
```

Le README (ton template `readme-projet`, Markdown du palier 0) est le document le plus rentable à soigner. L'ordre compte : le lecteur pressé lit le haut. Donc **le pitch et la démo en premier** — un lien cliquable vers l'app déployée et une capture valent tout le reste. Puis le problème, les fonctionnalités, la stack. Un README sans démo ni capture, qui commence par « installation », rate son lecteur.

### ⭐ Le portfolio : la vitrine des projets finis

```
Le portfolio présente 2 à 4 projets FINIS (pas dix brouillons). Pour chacun :
  - le pitch (une phrase),
  - une capture/démo,
  - les liens : app en ligne + code (GitHub) + README,
  - la stack en un coup d'œil.
Mieux vaut 2 projets finis et démontrables que 10 "en cours". (Qualité > quantité.)
Mets en avant le PRODUIT MULTI-CLIENTS (leçon 02) : il raconte tout ton parcours.
```

Le portfolio est ta vitrine. La règle d'or : **peu de projets, mais finis**. Deux ou trois produits aboutis, en ligne, démontrables, valent mieux qu'une liste de dix projets à moitié faits (qui signalent, au contraire, que tu ne finis pas — l'inverse de l'effet voulu). Mets ton produit multi-clients (leçon 02) en tête : il prouve le plus. Le portfolio peut être une page simple (même un README de profil GitHub bien fait suffit au début).

### GitHub soigné et épinglé

```
- Épingle tes 4-6 MEILLEURS dépôts sur ton profil (ceux avec un bon README et une démo).
- Chaque dépôt épinglé a un README qui raconte (ci-dessus).
- Un README de PROFIL (le dépôt à ton nom d'utilisateur) : qui tu es, ce que tu cherches, tes projets.
- Nettoie : les dépôts brouillons/vides ne sont pas épinglés (ils ne desservent pas s'ils sont discrets).
```

Ton GitHub est souvent la première chose qu'un recruteur technique ouvre. Épingle tes meilleurs projets (ceux avec README + démo), soigne le README de ton profil, et mets en avant la qualité plutôt que la quantité. Un GitHub où les projets épinglés sont tous finis et bien documentés raconte « cette personne livre et soigne son travail ».

### La présence professionnelle cohérente

```
Portfolio, GitHub, profil pro (LinkedIn/CV) doivent :
  - raconter la MÊME histoire (fullstack, les projets, ce que tu cherches),
  - pointer les uns vers les autres (le profil pro → le portfolio → GitHub → les démos),
  - être à JOUR (rien de pire qu'un profil abandonné à moitié rempli).
Le pitch de TOI-MÊME : une phrase sur qui tu es et ce que tu apportes (comme le pitch produit).
```

La cohérence est un signal de sérieux. Un recruteur recoupe : si ton profil pro, ton GitHub et ton portfolio se renvoient l'un à l'autre et racontent la même histoire, il te fait confiance. S'ils sont contradictoires ou abandonnés, il doute. Soigne aussi ton « pitch personnel » : une phrase claire sur qui tu es et ce que tu cherches.

### Les captures et les démos

```
Une IMAGE ou une DÉMO cliquable vaut mille mots :
  - capture d'écran de l'app (ou GIF animé d'un parcours clé),
  - lien vers l'app DÉPLOYÉE (palier 8) qu'on essaie en un clic.
C'est ce qui prouve, instantanément, que le projet est RÉEL et FINI.
```

Le visuel est ce qui capte le regard du lecteur pressé. Une capture montre que l'app existe et a une vraie interface ; un lien de démo prouve qu'elle tourne. C'est le dividende concret d'avoir déployé (palier 8) : tu peux dire « essaie », pas seulement « j'ai fait ».

## Les problèmes que tu vas rencontrer

**« J'ai du code sur GitHub mais personne ne comprend ce que c'est. »** Pas de README, ou un README qui commence par l'installation. Ajoute pitch + démo + capture en haut. Le code sans présentation est invisible.

**« J'ai dix projets mais aucun ne semble solide. »** La quantité dessert : dix brouillons signalent que tu ne finis pas. Épingle 2-4 projets **finis** et cache le reste. Qualité > quantité.

**« Mon README commence par "npm install". »** Tu écris pour toi, pas pour un étranger pressé. Commence par ce qu'il veut savoir d'abord : à quoi ça sert, une démo, une image. L'installation vient après.

**« Pas de démo, juste du code. »** Un lien de démo (app déployée, palier 8) et une capture sont ce qui convainc le plus. Déploie ton projet et mets le lien en haut du README.

**« Mon profil pro et mon GitHub racontent des choses différentes. »** Incohérence qui crée le doute. Aligne-les, fais-les pointer l'un vers l'autre, mets-les à jour.

**« Je ne sais pas me présenter en une phrase. »** Applique le pitch de la leçon 01 à toi-même : qui tu es, ce que tu apportes, ce que tu cherches. Si tu ne peux pas le dire en une phrase, c'est que ce n'est pas clair — travaille-le.

## Ce qu'on te demandera

En **recherche d'emploi**, ta présentation **est** le premier filtre : le recruteur regarde ton profil, ton GitHub, ton portfolio avant même de te parler. On n'attend pas que tu « demandes » — on te juge sur ce qu'on voit. Un profil clair, des projets finis avec démo, un README qui raconte, déclenchent l'entretien.

En **entretien** (leçon 05), on te dira souvent « parle-moi de ce projet » en regardant ton portfolio : ta présentation prépare directement cette conversation. Un projet bien présenté est un projet facile à raconter.

En **poste**, on attend que tu saches documenter (README, docs internes) — la même compétence, au service de l'équipe.

---

## Ce qui te démarquera

**Des projets finis, démontrables, bien racontés.** C'est ce qui fait la différence. Peu de candidats juniors ont un produit en ligne, avec une démo cliquable et un README clair. L'avoir — surtout le produit multi-clients (leçon 02) — te place immédiatement au-dessus de la pile.

**Le souci du lecteur pressé.** Présenter pour quelqu'un qui ne te connaît pas et qui survole, c'est penser à ton audience — une qualité professionnelle que le recruteur lit comme un signal. Le test des 90 secondes, appliqué, te distingue.

**La cohérence et le fini.** Un profil où tout (portfolio, GitHub, LinkedIn) se tient, est à jour et pointe vers des projets aboutis, raconte « cette personne soigne son travail et le mène au bout ». C'est exactement l'image qui recrute.

**Et savoir se pitcher.** Appliquer à toi-même le cadrage de la leçon 01 — une phrase claire sur qui tu es et ce que tu apportes — te prépare à chaque première impression, en ligne comme en entretien.

## 🛠️ À faire

1. **⭐ Le README principal** : écris le README de ton produit multi-clients (leçon 02) dans l'ordre du lecteur pressé : pitch, **démo + capture en haut**, problème, fonctionnalités, stack, lancement. Utilise ton template `readme-projet`.
2. **Le test des 90 secondes** : montre ce README à quelqu'un (ou imagine un étranger pressé) et vérifie qu'il comprend à quoi ça sert, que c'est fini, et où est le code. Corrige ce qui n'est pas clair.
3. **La démo et la capture** : assure-toi que le README contient un **lien vers l'app déployée** (palier 8) et au moins une capture d'écran (ou un GIF d'un parcours clé).
4. **⭐ Le portfolio** : présente 2 à 4 projets **finis**, chacun avec son pitch, sa capture, ses liens (démo + code) et sa stack. Mets le produit multi-clients en tête. Résiste à l'envie d'ajouter des projets inachevés.
5. **GitHub épinglé** : épingle tes meilleurs dépôts (ceux avec README + démo), et vérifie que chacun a un README qui raconte.
6. **Le README de profil** : crée (ou soigne) le README de ton profil GitHub : qui tu es, ce que tu cherches, tes projets phares.
7. **Le profil professionnel** : mets à jour ton profil (type LinkedIn) pour qu'il raconte la même histoire que ton portfolio et pointe vers lui et vers GitHub.
8. **⭐ Le pitch personnel** : écris en une phrase qui tu es et ce que tu apportes (comme le pitch produit de la leçon 01). Vérifie qu'elle est claire pour quelqu'un qui ne te connaît pas.
9. **La cohérence** : vérifie que portfolio, GitHub et profil pro se renvoient l'un à l'autre, racontent la même histoire, et sont à jour.
10. **Le lien** : dans ton journal, note comment le pitch (leçon 01) et les projets (leçons 02-03) alimentent ta présentation, et comment celle-ci prépare tes entretiens (leçon 05).
